# berman-ai-scan

שירות הפענוח של תעודות מאפיית ברמן. קובץ אחד (`server.js`), בלי תלויות,
Node 20+. הלקוח הוא `asafkiri/berman-app`.

```
npm start    # מאזין על PORT (ברירת מחדל 8080)
npm test     # בדיקות עוגן הביקורת
```

## עוגן הביקורת

### SERVICE_VERSION 5 — שתי קריאות ואימות נוסף

כל בקשת סריקת תעודה מפעילה שתי קריאות עצמאיות במקביל במודל הראשי
(`OPENAI_MODEL`, ברירת מחדל `gpt-5.6-luna`). משווים קודים, ברקודים,
כמויות, מחירים, מספר ותאריך תעודה וכל שדות הסיכום. שינוי בסדר השורות,
עיצוב התאריך או ניסוח תיאור המוצר אינו פער. שדות חיוניים חסרים אינם התאמה.

אי־התאמה, שדה חיוני לא קריא, ביטחון נמוך או סתירה בכמויות/בסיכום מפעילים
קריאה עצמאית אחת ב־`OPENAI_RETRY_MODEL` (ברירת מחדל `gpt-5.6-terra`).
המודל מקבל את הצילום המקורי ומיקום השדות לבדיקה, בלי תשובות קודמות ובלי
מחירים צפויים. אין תיקון מספרים כדי להתאים לקטלוג או לסכום.

באפליקציה v85, גם שתי קריאות תואמות עם מחיר חריג מול כל צורות המחיר
המותרות, או פער כספי בלתי מוסבר, מבקשות את קריאת האימות. זו בקשת
`mode: "verify"` באותו מסלול מאומת, עם `verificationTargets` המכילים
מיקום ושם שדה בלבד. כשהשרת כבר השתמש באימות, הלקוח אינו מבקש קריאה רביעית.
אחוז הנחה חסר אינו סיבה לקריאה נוספת. האפליקציה אינה משחזרת אוטומטית
בקשת מודל בתשלום אחרי כשל רשת, ואינה מפעילה שוב סריקות לאחר שחזור טיוטה.

התשובה כוללת `verification`, רשימת `reads` עם מודל/מזהה בקשה/שימוש לכל
קריאה, ו־`usage` המסכם את נתוני השימוש הזמינים מכל הקריאות. מצב
`needs_review` שומר את הנתונים לבדיקה; הוא אינו הסכמה או אישור מחיר.
התמונות אינן נשמרות בשירות. סריקת מכתב מבצעים וניתוח פערים אינם מוכפלים.

הבדיקות מדמות את גבולות האימות והמודל; הן אינן מדידה של דיוק OCR,
זמן או עלות על תעודות אמיתיות. בדיקת השרת הפעיל זמינה ב־`/health`
עם `scanStrategy: "dual-read-with-verification"`.

הבקשה יכולה לכלול `expectedUnits` ו-`expectedLines` — "סה"כ כללי" ו"שורות"
כפי שהוקלדו בלקוח. הם אינם חובה, ומה שנעשה בהיעדרם השתנה ב-**SERVICE_VERSION 3**:

| | הקריאה נמדדת מול | הערה |
|---|---|---|
| הוקלדו עוגנים | המספרים שהוקלדו | ההתנהגות הישנה, ללא שינוי |
| לא הוקלדו | **בלוק הסיכום שבתחתית אותו נייר** | v3 |

הלקוח מצלם עכשיו את התעודה לפני הקליטה וקורא ממנה את שלושת המספרים במקום
להקליד אותם, ולכן הוא שולח את שני השדות ריקים. עד v3 מסמך כזה דילג על כל
הבדיקה — וזה כיבה בשקט את שני המנגנונים שהיא מפעילה: **הקריאה החוזרת
המתקנת** (סבב שני ב-reasoning effort גבוה יותר, עם הנחיה מפורשת מה לא נסגר)
ו**הוויתור המיידי** על צילום שנקטע לפני בלוק הסיכום.

מעכשיו ההשוואה נעשית מול הנייר עצמו. בלוק הסיכום מודפס בנפרד מהשורות, ולכן
קריאה שגויה של כמות או של שורה אינה מסתדרת מולו:

- סכום הכמויות שנקראו מול `totalUnits` המודפס
- מספר השורות שנקראו מול `printedLines` המודפס

**SERVICE_VERSION 4:** בדיקת הכסף מתבצעת בלקוח בלבד. עמודת סכום השורה בתעודה ריקה, וגם פלט המודל אינו כולל `lineTotalExVat`. ב-v3 השדה החסר נסכם לאפס וגרם לניסיון תיקון מיותר גם בקריאה נכונה. גם הכפלת המחיר המודפס בכמות אינה תחליף: ההנחות הקבועות חבויות, וחלק מהמבצעים כבר ניתנו בתעודה בעוד אחרים יינתנו במרכזת.

ההנחיה למודל מכירה בשני מצבי מחיר לכל שורה, כולל ערבוב באותה תעודה. המודל מעתיק את המחיר המודפס בלי להפעיל הנחה ובלי לשנות מספר כדי לסגור את הסיכום. באפליקציה v67 שער האמון מחשב כל שורה לפי מחיר המבצע המודפס או לפי המחיר הרגיל אחרי ההנחה, ובודק מול הנטו המודפס.

זיהוי עוגן שגוי נשאר תלוי בהקלדה: `anchor_mismatch_printed` (הקריאה
תואמת את המודפס ורק המספר שהוקלד שונה) כבוי כשלא הוקלד דבר — אין מספר שיכול
להיות שגוי.


הבדיקות משתמשות במבנה השורות האמיתי של המודל. מסלול הבקשה נבדק בזיכרון עם חתימת אימות ומודל מדומים, בלי פתיחת חיבור רשת: קריאה תקינה מסתיימת בשתי קריאות מקבילות, ושגיאת כמות או מחיר מפעילה קריאת אימות שלישית לכל היותר.

## פריסה

מיזוג ל-`main` מריץ את `.github/workflows/deploy.yml`: קודם `npm test`,
ורק אם הוא עבר — `gcloud run deploy` של השירות `berman-ai-scan` באזור
`europe-west1`, ואז בדיקת `/health` על הכתובת שחזרה. פריסה שעלתה אך אינה
עונה נכשלת אדום במקום להיראות ירוקה.

**חיבור ההרשאה — פעם אחת.** עד שהיא מחוברת הריצה מסתיימת ירוקה עם הודעה,
ולא נכשלת בכל מיזוג. שתי אפשרויות, ב-Settings → Secrets and variables → Actions:

- **מומלץ — Workload Identity Federation** (בלי מפתח קבוע ב-GitHub):
  `GCP_WIF_PROVIDER` (מזהה מלא של ה-provider) ו-`GCP_SERVICE_ACCOUNT`
  (כתובת חשבון השירות).
- **פשוט יותר — מפתח חשבון שירות**: `GCP_SA_KEY` ובו ה-JSON המלא.

לחשבון השירות דרושים `roles/run.admin`, `roles/cloudbuild.builds.editor`,
`roles/artifactregistry.writer` ו-`roles/iam.serviceAccountUser`.

**משתני הסביבה אינם נוגעים בפריסה, בכוונה.** `OPENAI_API_KEY`,
`OPENAI_MODEL` ו-`OPENAI_RETRY_MODEL` מוגדרים על השירות עצמו ב-Cloud Run.
פריסה שמגדירה משתנים מחליפה את *כל* הקיימים, ולכן ה-workflow אינו מגדיר
אף אחד ומשמר את מה שכבר שם.

פריסה ידנית, אם צריך: `gcloud run deploy berman-ai-scan --source . --region europe-west1`
